# Анализ масштабируемости для максимальной конфигурации

## Сценарий
- **80 дверей** на 10 платах (CFG_MAX_DOORS = 80)
- **256 зависимостей** (CFG_MAX_EDGES = 256)
- **80 postCloseTimeouts**

## Расчет размера JSON для загрузки

### Размер одного элемента в JSON:

**Дверь (cfg_door_t):**
```json
{"techId":1,"drawingId":1,"nodeId":1,"localDoor":1,"type":"NO","comment":"Дверь 1"}
```
- Минимальный размер: ~80 байт
- С комментарием (32 байта): ~110 байт
- **80 дверей × 110 байт = ~8800 байт**

**Зависимость (cfg_edge_t):**
```json
{"srcGlobalDoorId":1,"dstGlobalDoorId":2}
```
- Размер: ~40 байт
- **256 зависимостей × 40 байт = ~10240 байт**

**PostCloseTimeout:**
```json
{"globalDoorId":1,"timeoutMs":5000}
```
- Размер: ~35 байт
- **80 postCloseTimeouts × 35 байт = ~2800 байт**

**Служебные поля:**
- projectName, openTimeoutMs, net: ~200 байт

**Форматирование JSON:**
- Запятые, скобки, пробелы: примерно +30% = ~6600 байт

### ИТОГО размер JSON:
**~8800 + ~10240 + ~2800 + ~200 + ~6600 = ~28640 байт ≈ 28 KB**

## Проблемы с текущими буферами

### 1. HTTP_BODY_MAX = 8192 байт ❌ КРИТИЧНО
- **Требуется:** ~28 KB
- **Доступно:** 8 KB
- **Недостаток:** ~20 KB (в 3.5 раза меньше!)

**Последствия:**
- Загрузка конфигурации будет **невозможна** для максимальной конфигурации
- Ошибка "Payload Too Large" (413) при попытке загрузки

### 2. Размер структуры project_config_t в RAM

**Расчет размера:**
```c
typedef struct {
    uint32_t formatVersion;              // 4 байта
    uint32_t seq;                        // 4 байта
    char projectName[32];                 // 32 байта
    uint32_t openTimeoutMs;              // 4 байта
    uint32_t postCloseTimeoutMs[80];      // 320 байт
    uint8_t doorCount;                    // 1 байт
    uint8_t reserved1[3];                 // 3 байта
    cfg_door_t doors[80];                 // 80 × 64 = 5120 байт
    uint16_t edgeCount;                   // 2 байта
    uint16_t reserved2;                   // 2 байта
    cfg_edge_t edges[256];                // 256 × 2 = 512 байт
    cfg_net_t net;                        // 20 байт
    uint32_t reserved_u32[32];            // 128 байт
} project_config_t;
```

**Размер cfg_door_t:**
```c
typedef struct {
    uint16_t techId;        // 2 байта
    uint16_t drawingId;     // 2 байта
    uint8_t nodeId;         // 1 байт
    uint8_t localDoor;      // 1 байт
    uint8_t type;           // 1 байт
    uint8_t reserved0;      // 1 байт
    char comment[32];       // 32 байта
    // Выравнивание до 8 байт: +4 байта
} cfg_door_t;  // = 44 байта (с выравниванием может быть 48-64)
```

**Размер cfg_edge_t:**
```c
typedef struct {
    uint8_t srcGlobalDoorId;  // 1 байт
    uint8_t dstGlobalDoorId;   // 1 байт
} cfg_edge_t;  // = 2 байта
```

**Размер cfg_net_t:**
```c
typedef struct {
    uint8_t dhcpEnabled;        // 1 байт
    uint8_t ip[4];               // 4 байта
    uint8_t netmask[4];          // 4 байта
    uint8_t gw[4];                // 4 байта
    uint16_t webPort;             // 2 байта
    uint32_t canBitrate;          // 4 байта
    uint16_t canOfflineTimeoutMs; // 2 байта
    // Выравнивание: +1 байт
} cfg_net_t;  // = 22 байта (с выравниванием ~24)
```

**Итого project_config_t:**
- Базовые поля: 4+4+32+4+320+1+3 = 368 байт
- doors[80]: 80 × 64 = 5120 байт (предполагая выравнивание)
- edges[256]: 256 × 2 = 512 байт
- net: 24 байта
- reserved: 128 байт
- **ИТОГО: ~6152 байт ≈ 6 KB**

### 3. Хранение в RAM

**Глобальная переменная:**
```c
project_config_t g_project_cfg;  // ~6 KB в статической памяти
```

**На стеке при парсинге:**
```c
static int put_config_full(...) {
    project_config_t cfg = g_project_cfg;  // Копия на стеке! ~6 KB
    // ...
}
```

**Проблема:** Копия структуры создается на стеке `httpTask`, что увеличивает использование стека.

### 4. Размер стека httpTask

**Текущий размер:** 4096 * 4 = **16384 байт (16 KB)**

**Использование стека:**
- `req_body[HTTP_BODY_MAX]` = 8192 байт (текущий размер)
- `resp[1024]` = 1024 байта
- `rx[768]` = 768 байт
- `hdr[256]` = 256 байт
- `cfg = g_project_cfg` (копия) = ~6152 байта
- Локальные переменные и стек вызовов = ~500-1000 байт

**Итого:** ~8192 + 1024 + 768 + 256 + 6152 + 1000 = **~17392 байт**

**Проблема:** При текущем размере стека (16 KB) и HTTP_BODY_MAX = 8192 байт уже используется ~17 KB, что **превышает размер стека**!

## Рекомендации по исправлению

### Вариант 1: Увеличить HTTP_BODY_MAX до 32 KB (рекомендуется)

**Изменения:**
```c
// App/system/http_server.c
#define HTTP_BODY_MAX 32768  // 32 KB для максимальной конфигурации
```

**Плюсы:**
- Простое решение
- Поддерживает максимальную конфигурацию
- Оставляет запас для будущих расширений

**Минусы:**
- Увеличивает использование стека на ~24 KB
- Требует увеличения стека httpTask

### Вариант 2: Увеличить стек httpTask

**Изменения:**
```c
// Core/Src/freertos.c
const osThreadAttr_t httpTask_attributes = {
  .name = "httpTask",
  .stack_size = 8192 * 4,  // Было: 4096 * 4, Стало: 32768 байт (32 KB)
  .priority = (osPriority_t) osPriorityNormal,
};
```

**Необходимо при:**
- HTTP_BODY_MAX = 32768 байт
- Копия project_config_t на стеке (~6 KB)

**Итого использование стека:**
- req_body[32768] = 32768 байт
- resp[1024] = 1024 байта
- rx[768] = 768 байт
- hdr[256] = 256 байт
- cfg (копия) = 6152 байта
- Локальные переменные = ~1000 байт
- **Итого: ~46968 байт ≈ 46 KB**

**Рекомендуемый размер стека:** 48 KB (12288 * 4)

### Вариант 3: Избежать копии project_config_t на стеке (оптимизация)

**Изменения:**
```c
// App/system/http_api.c
static int put_config_full(const char *body, size_t body_len, char *out_body, size_t out_sz)
{
    // Вместо копии на стеке, работаем напрямую с g_project_cfg
    project_config_t *cfg = &g_project_cfg;  // Указатель вместо копии
    
    // Или использовать статический буфер
    static project_config_t s_cfg_buffer;
    project_config_t *cfg = &s_cfg_buffer;
    *cfg = g_project_cfg;  // Копия в статической памяти, не на стеке
    // ...
}
```

**Плюсы:**
- Экономит ~6 KB стека
- Можно использовать меньший стек httpTask

**Минусы:**
- Требует синхронизации (один запрос за раз)
- Увеличивает использование статической памяти

### Вариант 4: Потоковая обработка JSON (сложное решение)

**Идея:** Парсить JSON по частям, не загружая весь в память.

**Плюсы:**
- Минимальное использование памяти
- Поддерживает конфигурации любого размера

**Минусы:**
- Сложная реализация
- Требует переработки JSON парсера

## Рекомендуемое решение

### Комбинированный подход:

1. **Увеличить HTTP_BODY_MAX до 32 KB:**
   ```c
   #define HTTP_BODY_MAX 32768
   ```

2. **Увеличить стек httpTask до 48 KB:**
   ```c
   .stack_size = 12288 * 4,  // 48 KB
   ```

3. **Оптимизировать использование памяти (опционально):**
   - Использовать указатель вместо копии project_config_t
   - Или вынести копию в статическую память

### Итоговые требования:

- **HTTP_BODY_MAX:** 32768 байт (32 KB)
- **Стек httpTask:** 49152 байт (48 KB)
- **Статическая память:** g_project_cfg = 6152 байта (6 KB)
- **Общее использование RAM:** ~57 KB для HTTP обработки

### Проверка доступной памяти:

**STM32H723:**
- **RAM_D1:** 320 KB
- **DTCMRAM:** 128 KB
- **ITCMRAM:** 64 KB

**Использование:**
- FreeRTOS heap: 64 KB
- Стеки задач: ~50 KB (включая httpTask 48 KB)
- Статические буферы: ~10 KB
- g_project_cfg: 6 KB
- **Итого:** ~130 KB из 320 KB (RAM_D1) - **достаточно**

## Выводы

### ❌ Текущее состояние:
- **HTTP_BODY_MAX = 8192 байт** - недостаточно для максимальной конфигурации (28 KB)
- **Стек httpTask = 16 KB** - недостаточно при увеличении HTTP_BODY_MAX
- Загрузка конфигурации на 80 дверей **невозможна**

### ✅ После исправлений:
- **HTTP_BODY_MAX = 32 KB** - достаточно для максимальной конфигурации
- **Стек httpTask = 48 KB** - достаточно для обработки
- Загрузка конфигурации на 80 дверей **возможна**
- Достаточно памяти в STM32H723

### ⚠️ Важно:
- При текущих настройках система **не сможет** загрузить максимальную конфигурацию
- Необходимо увеличить буферы и стек перед использованием 80 дверей
- Для конфигураций до 16 дверей текущие настройки достаточны
