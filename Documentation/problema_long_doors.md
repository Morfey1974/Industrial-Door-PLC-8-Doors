# Проблема долгого зависания ответа по /api/doors

## Описание проблемы

При запросе `http://192.168.1.50/api/doors` в браузере возникали следующие проблемы:

1. **Долгое ожидание ответа** - запрос зависал на несколько минут
2. **Ошибка `net::ERR_CONTENT_LENGTH_MISMATCH`** - несоответствие заявленной и фактической длины ответа
3. **Пустое окно браузера** - данные не отображались
4. **Блокировка при множественных запросах** - при нажатии F5 несколько раз браузер полностью зависал и требовался ресет платы

## Причины проблемы

### 1. Блокирующие таймауты в HTTP сервере
- `lwip_select` с таймаутом **2 секунды** для ожидания данных от клиента
- Таймауты сокета `SO_RCVTIMEO` и `SO_SNDTIMEO` установлены на **2 секунды**
- При медленном подключении клиента HTTP задача блокировалась на долгое время

### 2. Отсутствие синхронизации доступа к данным дверей
- `Doors_GetState()` читал данные из массива `s_doors` без защиты мьютексом
- Возможны race conditions при одновременном доступе из разных задач
- `updateOneDoor()` использовал `portMAX_DELAY` - бесконечное ожидание мьютекса

### 3. Неэффективное использование мьютекса
- `build_doors()` вызывал `Doors_GetState()` **8 раз подряд** (для каждой двери)
- Каждый вызов захватывал и освобождал мьютекс отдельно
- Это создавало множественные блокировки и замедляло обработку

### 4. Проблемы с отправкой данных в non-blocking режиме
- В non-blocking режиме `lwip_send()` может не отправить все данные сразу
- Старый код прерывал отправку при ошибке, но `Content-Length` уже был указан
- Фактически отправленное количество байт не совпадало с заявленным в заголовке

### 5. Недостаточный размер буфера
- Буфер `body[2048]` мог быть недостаточным для JSON с 8 дверьми
- При переполнении буфера данные терялись

## Решение

### 1. Уменьшение таймаутов (`App/system/http_server.c`)
```c
// Было: tv_client.tv_sec = 2;
// Стало:
tv_client.tv_sec = 0;
tv_client.tv_usec = 100000; /* 100ms таймаут вместо 2 секунд */

// Было: tv_timeout.tv_sec = 2;
// Стало:
tv_timeout.tv_sec = 0;
tv_timeout.tv_usec = 200000; /* 200ms таймаут вместо 2 секунд */
```

### 2. Добавление мьютекса для синхронизации (`App/doors/doors_task.c`)
```c
static SemaphoreHandle_t s_doors_mutex = NULL;

// Инициализация в Doors_TaskInit()
if (!s_doors_mutex) {
    s_doors_mutex = xSemaphoreCreateMutex();
}

// Использование в updateOneDoor()
if (s_doors_mutex) {
    if (xSemaphoreTake(s_doors_mutex, pdMS_TO_TICKS(50)) != pdTRUE) {
        return; /* Пропускаем итерацию при таймауте */
    }
}
// ... обновление данных ...
if (s_doors_mutex) {
    xSemaphoreGive(s_doors_mutex);
}
```

### 3. Оптимизация доступа к данным (`App/system/http_api.c`)
```c
// Было: 8 вызовов Doors_GetState() - 8 захватов мьютекса
// Стало: один захват мьютекса для всех дверей
AppDoorState_t *doors_array = Doors_GetStateArrayLocked();
if (!doors_array) {
    return jw_appendf(w, "]}"); // Пустой список при ошибке
}

for (uint8_t i = 1; i <= APP_DOOR_MAX; i++) {
    uint8_t idx = (uint8_t)(i - 1U);
    AppDoorState_t st = doors_array[idx]; // Прямой доступ
    // ... обработка ...
}

Doors_ReleaseStateArray(); // Освобождаем мьютекс один раз
```

### 4. Улучшение отправки данных (`App/system/http_server.c`)
```c
// Проверка готовности сокета к записи через select
fd_set wfds;
FD_ZERO(&wfds);
FD_SET(fd, &wfds);
int sel_ready = lwip_select(fd + 1, NULL, &wfds, NULL, &tv_select);

if (sel_ready > 0) {
    // Отправляем небольшими блоками (256 байт)
    size_t chunk_size = (size_t)(body_len - sent);
    if (chunk_size > 256) chunk_size = 256;
    
    int r = lwip_send(fd, body + sent, chunk_size, 0);
    // Повторяем попытки до полной отправки
}
```

### 5. Увеличение размера буфера (`App/system/http_server.c`)
```c
// Было: char body[2048];
// Стало:
char body[4096]; // Увеличен для JSON с 8 дверьми
memset(body, 0, sizeof(body)); // Инициализация нулями
```

### 6. Добавление задержки после отправки заголовка
```c
// Небольшая задержка после отправки заголовка для обработки в lwIP
if (body_len > 0) {
    osDelay(2); /* 2мс задержка */
}
```

## Новые функции

### `Doors_GetStateArrayLocked()` и `Doors_ReleaseStateArray()`
Добавлены в `App/doors/doors_task.c` для безопасного массового доступа к данным дверей:
```c
AppDoorState_t* Doors_GetStateArrayLocked(void);
void Doors_ReleaseStateArray(void);
```

## Результат

После всех исправлений:
- ✅ Ответ `/api/doors` приходит быстро (менее 500мс вместо нескольких минут)
- ✅ Данные дверей защищены от race conditions через мьютекс
- ✅ HTTP мониторинг не блокирует работу дверей
- ✅ Система остается отзывчивой даже при работе с конфигурацией
- ✅ Нет ошибки `ERR_CONTENT_LENGTH_MISMATCH`
- ✅ Множественные запросы (F5) не вызывают зависание

## Технические детали

### Производительность
- **До:** 8 захватов мьютекса + 8 освобождений = 16 операций
- **После:** 1 захват + 1 освобождение = 2 операции
- **Ускорение:** в 8 раз меньше операций с мьютексом

### Безопасность
- Мьютекс с таймаутом 50мс в `updateOneDoor` - предотвращает бесконечные блокировки
- Мьютекс с таймаутом 100мс в `Doors_GetStateArrayLocked` - быстрый отказ при недоступности
- Если мьютекс недоступен, возвращается пустой список вместо зависания

### Надежность
- Разбиение отправки на блоки по 256 байт
- Проверка готовности сокета через `select` перед отправкой
- Повторные попытки отправки до полной передачи данных

## Дата решения

Проблема решена в процессе разработки Этапа 9 (Ethernet + HTTP/REST API).
