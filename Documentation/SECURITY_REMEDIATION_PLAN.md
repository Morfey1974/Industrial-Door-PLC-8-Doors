# Поэтапный план устранения проблем безопасности

Документ описывает поэтапный план устранения выявленных уязвимостей и усиления защиты Industrial Door PLC (прошивка + WebUI). Каждый этап содержит действия и перечень файлов для изменений.

---

## Этап 1. Проверка токена на API и защита чувствительных маршрутов

**Цель:** Все чувствительные GET/PUT требуют валидный токен (или сессию); публичными остаются только логин и, при необходимости, сброс пароля по токену.

| № | Действие | Файлы |
|---|----------|--------|
| 1.1 | Ввести общую функцию проверки токена: из заголовка `Authorization: Bearer <token>` или из query/body, проверка формата и (позже) подписи/срока. | `App/system/http_api.c`, новый вспомогательный код в `http_api.c` или `App/system/users_service.c` (если токены хранятся/проверяются там) |
| 1.2 | Хранить или проверять сессионные токены после логина: либо список активных токенов в RAM (users_service / отдельный модуль), либо подписанный JWT-like токен с username и expiry, проверяемый без хранения. | `App/system/users_service.c`, `App/system/users_service.h`; при выборе JWT — `App/system/http_api.c` + малая крипто-библиотека или HAL |
| 1.3 | В `HttpApi_HandleGet`: для `/api/state`, `/api/doors`, `/api/config`, `/api/config/full`, `/api/config/mapping`, `/api/journal/*` вызывать проверку токена; при отсутствии/невалидном — 401. Исключение: только `/api/auth/login` и, по желанию, `/api/auth/reset-password` (по токену сброса). | `App/system/http_api.c` |
| 1.4 | В `HttpApi_HandlePut`: для `/api/config`, `/api/config/full`, `/api/config/mapping`, `/api/users/*` требовать валидный токен и при необходимости проверять роль (например, только admin/super_admin для config и users). | `App/system/http_api.c` |
| 1.5 | В `HttpApi_HandlePost`: для `/api/auth/change-password`, `/api/auth/forgot-password`, `/api/users`, `/api/users/.../delete` и т.п. — проверять токен и подставлять `current_user` из токена, а не из body/query (убрать доверие к `currentUser` из запроса). | `App/system/http_api.c` |
| 1.6 | Передавать в API путь и заголовки (или сырой буфер заголовков), чтобы парсить `Authorization: Bearer <token>`. | `App/system/http_server.c` — при вызове `HttpApi_HandleGet`/`HandlePut`/`HandlePost` передавать заголовки или указатель на начало буфера запроса; `App/system/http_api.h` — обновить сигнатуры при необходимости |

**Результат этапа:** Все данные и изменение конфигурации/пользователей возможны только при валидном токене; подмена `currentUser` в body больше не даёт прав.

## Этап 2. Отправка токена с WebUI и «сессия» в браузере

**Цель:** Клиент отправляет токен с каждым запросом; сервер его проверяет.

| № | Действие | Файлы |
|---|----------|--------|
| 2.1 | В axios-интерцепторе запроса читать `localStorage.getItem('auth_token')` и, если есть, добавлять заголовок `Authorization: Bearer <token>`. | `WebUI/src/services/api.js` |
| 2.2 | При ответе 401 — очищать токен и редиректить на страницу входа (или вызывать logout в AuthContext). | `WebUI/src/services/api.js` (response interceptor), при необходимости `WebUI/src/context/AuthContext.jsx` |
| 2.3 | Опционально: реализовать `GET /api/auth/session` или `GET /api/auth/me`, который по заголовку `Authorization` возвращает данные пользователя или 401; использовать для проверки сессии при загрузке приложения вместо опоры только на localStorage. | `App/system/http_api.c` (новый обработчик GET), `WebUI/src/services/auth.js` (`getSession` вызывает этот endpoint с токеном) |

**Результат этапа:** Все запросы к API идут с токеном; неавторизованный доступ к данным с клиента прекращается после 401.

---

## Этап 3. Хранение паролей: сильный хеш и соль

**Цель:** Пароли хранятся в виде стойкого хеша с криптостойкой солью.

| № | Действие | Файлы |
|---|----------|--------|
| 3.1 | Реализовать SHA-256: либо через HAL (STM32H7 HASH), либо компактную библиотеку (e.g. mbedtls в проекте или отдельный tiny-SHA256). Заменить текущий `simple_hash` на SHA-256(password \|\| salt) или лучше PBKDF2-HMAC-SHA256 (итерации, соль). | `App/config/password_hash.c`, `App/config/password_hash.h`; при использовании HAL — `Core/Inc/stm32h7xx_hal_conf.h` (включить HASH), драйвер в `Core/` или `App/` |
| 3.2 | Генерация соли: использовать аппаратный RNG (HAL RNG) вместо `HAL_GetTick()`. | `App/config/password_hash.c` |
| 3.3 | Миграция: при первом входе после обновления прошивки проверять старый формат хеша и при успешной проверке перезаписывать пароль уже новым хешем (опционально, если нужно сохранить старых пользователей). | `App/config/password_hash.c` или `App/system/users_service.c` |

**Результат этапа:** Утечка хранилища пользователей не даёт восстановить пароли без перебора; соль и итерации усложняют атаки.

## Этап 4. Токен сброса пароля: криптостойкая случайность

**Цель:** Токен сброса нельзя предсказать по имени пользователя и времени.

| № | Действие | Файлы |
|---|----------|--------|
| 4.1 | Генерация токена: 32 байта (или 16) из HAL RNG, сохранять в виде hex-строки. Убрать зависимость от username + tick. | `App/system/users_service.c` |
| 4.2 | Хранить токен, username, время истечения и «used» в существующей структуре; при сбросе пароля помечать токен использованным. | `App/system/users_service.c` (уже есть, проверить формат хранения под новый токен) |

**Результат этапа:** Токен сброса непредсказуем и одноразовый.

---

## Этап 5. Ограничение CORS

**Цель:** API не вызывается произвольными сайтами из интернета.

| № | Действие | Файлы |
|---|----------|--------|
| 5.1 | Вместо `Access-Control-Allow-Origin: *` подставлять конкретный origin из конфига (например, базовый URL WebUI) или разрешать только пустой origin (локальные файлы/устройство). При отсутствии конфига — оставить `*` только для режима отладки (опционально). | `App/system/http_server.c` (места формирования заголовков с `Access-Control-Allow-Origin`) |
| 5.2 | При необходимости хранить разрешённый origin в конфиге проекта (например, `net.allowedOrigin` или отдельная настройка). | `App/config/config_format.c`, `App/config/config_format.h` (новое поле), при необходимости WebUI/конфиг-страница |

**Результат этапа:** Запросы к API возможны только с разрешённого источника.

## Этап 6. Защита от перебора паролей (логин)

**Цель:** Ограничить brute-force по логину.

| № | Действие | Файлы |
|---|----------|--------|
| 6.1 | Ввести счётчик неудачных попыток входа по IP или по имени пользователя (в RAM, сброс по времени). При превышении порога (например, 5 за 15 минут) возвращать 429 или 401 с задержкой ответа (например, 2–5 секунд). | `App/system/http_api.c` (в `post_auth_login`), при необходимости небольшой модуль в `App/system/` для учёта попыток |
| 6.2 | Не сообщать в ответе, что именно неверно — «логин» или «пароль»; единое сообщение «Invalid credentials». | `App/system/http_api.c` (уже так, проверить и зафиксировать) |

**Результат этапа:** Массовый перебор паролей затруднён.

---

## Этап 7. Формат токена после логина (устойчивость к подделке)

**Цель:** Токен нельзя подделать без знания секрета или приватного ключа.

| № | Действие | Файлы |
|---|----------|--------|
| 7.1 | Вариант A: сервер при логине генерирует случайный токен (HAL RNG), сохраняет в таблице активных сессий (username, token, expiry). При каждом запросе API ищет токен в заголовке и проверяет по таблице. | `App/system/users_service.c` (или новый `App/system/session_service.c`), `App/system/http_api.c` |
| 7.2 | Вариант B: токен в виде подписанной строки (например, HMAC-SHA256(secret, username\|expiry)) с expiry в payload; сервер хранит только секрет, проверяет подпись и срок. Секрет при первом запуске сгенерировать через RNG и сохранить в QSPI/Flash. | `App/system/http_api.c` или отдельный модуль, `App/config/` (хранение секрета) |
| 7.3 | Установить срок жизни токена (например, 24 часа) и при необходимости продлевать при активности или требовать повторный логин. | Там же, где хранятся/проверяются сессии |

**Результат этапа:** Подделка токена без секрета/доступа к устройству невозможна.

## Этап 8. HTTPS (шифрование трафика)

**Цель:** Трафик между браузером и контроллером шифруется.

| № | Действие | Файлы |
|---|----------|--------|
| 8.1 | Включить mbedTLS (или аналог) в проекте, собрать lwIP с TLS (например, сокеты mbedtls + lwIP). | `Core/` (драйверы), проект CubeIDE (библиотеки), `Core/Src/lwip_bringup.c` / опции lwIP |
| 8.2 | Реализовать приём TLS на том же порту (или отдельном, например 443): инициализация сертификата и ключа сервера (желательно хранить в защищённой области или подписывать при сборке). | `App/system/http_server.c` (или новый `App/system/https_server.c`), конфиг порта в `App/config/` или `g_project_cfg` |
| 8.3 | В документации и WebUI указать использование HTTPS и предупреждение при доступе по HTTP (например, в SystemParams или при первом подключении). | `WebUI/src/pages/Settings/SystemParams.jsx`, `API_CONTRACT.md`, при необходимости `WebUI/src/utils/constants.js` (схема по умолчанию) |

**Результат этапа:** Перехват и подмена трафика без доступа к сертификату/ключу затруднены.

## Рекомендуемый порядок внедрения

1. **Сначала:** Этапы 1 и 2 (проверка токена на API + отправка токена с WebUI) — сразу закрывают неавторизованный доступ к данным и конфигурации.
2. **Затем:** Этапы 3 и 4 (хеш паролей, токен сброса) — укрепляют хранение и восстановление пароля.
3. **Потом:** Этапы 5, 6, 7 (CORS, rate limit, формат токена) — усиление политик и устойчивость к подделке.
4. **В конце:** Этап 8 (HTTPS) — требует больше изменений в стеке и сборке.
