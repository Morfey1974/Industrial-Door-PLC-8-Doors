# Проверка этапа 1+2: токен на API и отправка с WebUI

После внедрения первого пункта плана (Этапы 1 и 2) выполните проверки ниже.

## Что сделано

- **Прошивка:** все GET/PUT/POST к `/api/*` (кроме `/api/auth/login` и `/api/auth/reset-password`) требуют заголовок `Authorization: Bearer <token>`. Токен выдаётся при успешном логине и хранится в сессиях (RAM, 24 ч). Без токена или с невалидным/истёкшим токеном возвращается **401** и тело `{"ok":0,"error":"Unauthorized"}`.
- **WebUI:** при каждом запросе в заголовок подставляется `Authorization: Bearer <token>` из `localStorage`. При ответе **401** токен и пользователь очищаются и выполняется переход на `/login`.
- **GET /api/auth/session:** по валидному токену возвращает `{ "ok": 1, "user": { "username", "role" } }`; при загрузке приложения сессия проверяется через этот endpoint.

## Проверки

### 1. Запрос без токена (401)

- **Через браузер:** откройте WebUI, очистите `localStorage` (или откройте в режиме инкогнито), зайдите на страницу, требующую данных (Дашборд, Двери и т.п.). Должен произойти редирект на `/login`.
- **Через curl (замените IP/порт на свои):**
  ```bash
  curl -s -o /dev/null -w "%{http_code}" http://192.168.1.50/api/doors
  ```
  Ожидается **401**.

### 2. Логин и доступ с токеном (200)

- Войдите в WebUI под учётной записью (логин/пароль). После входа все запросы должны проходить с токеном.
- В UART (если включён лог) при успешном логине должно появиться сообщение вида: `[USERS] Session created for <username>` и `AUTH: login success for <username> (role=...)`.

### 3. Невалидный/истёкший токен (401)

- В UART при запросе без токена: `AUTH: request without valid Bearer token`.
- При запросе с неверным или истёкшим токеном: `AUTH: invalid or expired token`.

### 4. GET /api/auth/session

- С валидным токеном:
  ```bash
  curl -s -H "Authorization: Bearer <token>" http://192.168.1.50/api/auth/session
  ```
  Ожидается JSON: `{"ok":1,"user":{"username":"...","role":"..."}}`.
- Без заголовка или с неверным токеном — **401**.

### 5. Пользователи и смена пароля

- Страница «Пользователи» и смена пароля работают по токену; передавать `currentUser` в теле/query больше не нужно — текущий пользователь определяется по сессии.

## Отладка в мониторе (UART)

При `HTTP_DEBUG_ENABLED 1` в `http_server.h` в лог выводятся запросы и ответы. В лог пишутся также:

- `AUTH: request without valid Bearer token` — запрос без Bearer-токена;
- `AUTH: invalid or expired token` — токен не найден в сессиях или истёк;
- `[USERS] Session created for <username>` — после успешного логина создана сессия.

По ним можно убедиться, что защищённые маршруты требуют токен и что сессии создаются при входе.
