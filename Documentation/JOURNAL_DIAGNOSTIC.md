# Диагностика журнала событий

## Где хранятся события?

События хранятся в **QSPI Flash памяти** контроллера:

- **Адрес в Flash:** `0xF80000` (QSPI_EVENT_LOG_BASE)
- **Размер области:** 512 КБ (QSPI_EVENT_LOG_SIZE)
- **Размер сектора:** 4 КБ (QSPI_SECTOR_SIZE)
- **Количество секторов:** 128
- **Размер одной записи:** 32 байта
- **Записей на сектор:** 120 (3840 байт данных + 256 байт заголовок = 4096 байт)
- **Максимум записей:** ~15,360 записей (128 секторов × 120 записей)
- **Максимум памяти для данных:** ~480 КБ (512 КБ - заголовки секторов)

## Как проверить журнал через UART?

Подключитесь к контроллеру через UART3 (обычно это отладочный UART) и используйте CLI команды:

### Доступные команды:

1. **`log help`** - показать справку по командам
2. **`log stat`** - краткая статистика журнала
3. **`log info`** - подробная информация о журнале (количество записей, занятая память)
4. **`log recinfo`** - информация о размере записей и емкости
5. **`log dump [N]`** - вывести последние N записей (по умолчанию 20, максимум 200)
6. **`log clear`** - очистить журнал (стереть все события)

### Примеры использования:

```
log stat          # Краткая статистика
log info          # Подробная информация
log dump          # Последние 20 записей
log dump 50       # Последние 50 записей
log dump 200      # Последние 200 записей (максимум)
```

### Формат вывода статистики:

**`log stat`** выводит:
```
JOURNAL: base=0xF80000 size=524288 sect=4096 cnt=128 cur=0 seq=1 rec=0 drop=0 io=0
```

Где:
- `base` - адрес начала области журнала
- `size` - размер области (512 КБ = 524288 байт)
- `sect` - размер сектора (4 КБ = 4096 байт)
- `cnt` - количество секторов (128)
- `cur` - текущий сектор (0..127)
- `seq` - последовательность сектора (увеличивается при перезаписи)
- `rec` - всего записей записано
- `drop` - потеряно записей из очереди (если очередь переполнена)
- `io` - ошибки ввода/вывода

**`log info`** выводит подробную информацию:
```
=== ЖУРНАЛ СОБЫТИЙ - ДЕТАЛЬНАЯ ИНФОРМАЦИЯ ===
Адрес в Flash: 0xF80000
Общий размер: 512 КБ (524288 байт)
Размер сектора: 4096 байт
Количество секторов: 128
---
Текущий сектор: 0
Последовательность сектора: 1
---
Всего записей записано: 0
Максимум записей (теоретически): ~15360
Записей на сектор: 120
---
Занято секторов: ~0
Занято памяти: ~0 КБ (~0 байт)
Свободно памяти: ~512 КБ
---
Ошибки записи: 0
Потеряно из очереди: 0
===========================================
```

### Формат вывода записей:

**`log dump`** выводит записи в формате:
```
JLOG #123 t=1234567890 DOOR_OPEN(1) door=1 src=DOOR_LOCAL(1) arg=0x00000000 flags=0x00
```

Где:
- `#123` - номер записи (recSeq)
- `t=1234567890` - timestamp (в тиках FreeRTOS)
- `DOOR_OPEN(1)` - тип события и его код
- `door=1` - ID двери
- `src=DOOR_LOCAL(1)` - источник события и его код
- `arg=0x00000000` - дополнительный аргумент
- `flags=0x00` - флаги события

## Почему может быть пустой журнал?

1. **Журнал действительно пустой** - если контроллер только что запущен или журнал был очищен
2. **События не генерируются** - проверьте, что система работает и двери открываются/закрываются
3. **Ошибка чтения из QSPI** - проверьте `io_errors` в статистике
4. **Журнал не инициализирован** - проверьте, что `JournalTask` запущен

## Диагностика проблемы "Нет событий в журнале"

1. **Проверьте статистику:**
   ```
   log stat
   ```
   Если `rec=0`, значит журнал действительно пустой.

2. **Проверьте, генерируются ли события:**
   - Откройте/закройте дверь
   - Подождите несколько секунд
   - Выполните `log dump 10` - должны появиться новые записи

3. **Проверьте ошибки:**
   - Если `io_errors > 0` - проблема с чтением/записью в QSPI
   - Если `drop > 0` - очередь переполнена, события теряются

4. **Проверьте HTTP API:**
   - Откройте в браузере: `http://192.168.1.50/api/journal/stat`
   - Должна вернуться статистика в JSON формате
   - Откройте: `http://192.168.1.50/api/journal/dump?offset=0&limit=20`
   - Должны вернуться записи (или пустой массив, если журнал пустой)
