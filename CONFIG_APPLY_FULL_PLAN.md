# Вариант A: полная загрузка конфигурации в контроллер

## Цель

Сделать так, чтобы при нажатии «Применить на контроллер» в Web UI **на контроллер уходила и сохранялась в QSPI** полная конфигурация: не только `projectName` и `openTimeoutMs`, но и **двери** (`doors`), **зависимости** (`edges`), **индивидуальные таймауты** (`postCloseTimeouts`).  
«Загрузка с контроллера» и доработки UI (вариант B) — позже.

**Лимит первой версии:** не более **8 дверей** (и соответствующие ограничения на `edges` / `postCloseTimeouts`). Для начальных проверок этого достаточно; расширение — позже.

---

## Запись и активация конфигурации. Защита при обрыве связи

Вопрос: что если запись конфигурации началась, контроллер стёр старую конфигурацию, и в этот момент связь пропала? Не потеряем ли мы и старую, и новую конфигурацию?

**Ответ: так уже сделано.** Текущая реализация (`config_storage_qspi.c`, `config_layout.h`) работает по схеме **два слота A/B** и **запись в неактивный слот**:

1. **Два слота в QSPI:** Slot A (0xFE0000), Slot B (0xFF0000), по 64 KiB. Активная конфигурация хранится **в одном** из них.

2. **Новая конфигурация пишется только в неактивный слот:**
   - Определяем, какой слот сейчас активен (по `used_slot` при загрузке).
   - Целевой слот = **другой** (если активен A → пишем в B, и наоборот).
   - **Активный слот не трогаем** на всём протяжении записи.

3. **Порядок записи в целевой слот:**  
   `erase` (все секторы слота) → `payload` (структура `project_config_t`) → **commit** (заголовок `cfg_slot_header_t` с magic, seq, CRC) **последним**.

4. **Активация:** Слот считается валидным только если в нём есть **валидный commit-заголовок** (magic, CRC, formatVersion). При старте читаем оба заголовка, выбираем валидный слот с максимальным `seq`.

5. **Обрыв связи / сбой питания:**
   - **До записи commit:** в целевом слоте есть только erase + payload, заголовка нет или он невалидный → при следующем старте этот слот **игнорируется**, используется **старый активный** (он не тронут). Старая конфигурация сохраняется.
   - **После записи commit:** новый слот валиден → при старте выбирается он. Старый конфиг в другом слоте остаётся на флеше, но не используется.

Итого: сначала всегда пишем в **другое** место относительно текущей активной конфигурации; «замена» — это лишь смена выбора слота при следующем чтении, после успешной записи commit. Мусора и потери старой конфигурации при обрыве в процессе записи не происходит.

## Логирование в монитор при отладке

На протяжении всей отладки загрузки конфигурации в контроллер добавлять **вывод в UART (монитор логов)** на ключевых этапах:

- **HTTP API (`put_config_full`):** приём тела, начало парсинга, разбор `doors` / `edges` / `postCloseTimeouts` (количество элементов, ошибки парсинга), валидация, вызов persist, отправка ответа.
- **Config storage (`ConfigStorage_SaveNew`):** выбор целевого слота (A/B), этапы erase / payload / commit, тайминги, ошибки.

Используем имеющиеся `AppLog` и при необходимости `printf` для коротких маркеров. Это позволит сразу видеть проблемы при тестах (curl, UI).

## Текущее состояние

- **UI**: при «Применить» вызывается `putConfig(serverConfig)`; в `serverConfig` **сознательно** передаются только `projectName` и `openTimeoutMs` (комментарий в коде: firmware пока это не парсит).
- **Firmware**: 
  - `PUT /api/config` (merge) — парсит только `projectName`, `openTimeoutMs`, опционально `net`. Persist и ответ 200 работают.
  - `PUT /api/config/full` — использует тот же парсер; в коде явный TODO на разбор `doors`, `edges`, `postCloseTimeouts`. Сейчас по сути дублирует merge.
- **GET /api/config/full**: уже отдаёт полную конфиг в JSON (`doors`, `edges`, `postCloseTimeouts`, `net`). Формат совпадает с тем, что UI хранит у себя и будет отправлять.

## Контракт JSON (формат «полной» конфигурации)

Ориентир — вывод `build_config_full()` и структуры `config_format.h`. При **применении** (PUT) UI должен слать объект в том же формате.

### 1. `doors` — массив объектов

```json
"doors": [
  {
    "techId": 1,
    "drawingId": 0,
    "nodeId": 1,
    "localDoor": 1,
    "globalDoorId": 1,
    "type": "NC",
    "typeCode": 0,
    "comment": "..."
  }
]
```

- `techId`, `drawingId`, `nodeId`, `localDoor`, `globalDoorId`, `type`/`typeCode`, `comment` — соответствуют `cfg_door_t`.
- `globalDoorId` можно не слать, а вычислять на firmware по `Config_MakeGlobalDoorId(nodeId, localDoor)`; если слать — использовать для проверки.

### 2. `edges` — массив зависимостей

```json
"edges": [
  { "srcGlobalDoorId": 1, "dstGlobalDoorId": 2 }
]
```

- Прямое соответствие `cfg_edge_t`: `srcGlobalDoorId`, `dstGlobalDoorId` (1..80).

### 3. `postCloseTimeouts` — массив таймаутов

```json
"postCloseTimeouts": [
  { "globalDoorId": 1, "timeoutMs": 5000 }
]
```

- На firmware: `cfg.postCloseTimeoutMs[globalDoorId - 1] = timeoutMs`.

### 4. Остальное

- `projectName`, `openTimeoutMs` — как сейчас.
- `net` — по желанию (dhcpEnabled, webPort); уже есть парсинг в merge.

## Где менять

### Firmware

1. **`put_config_full` (http_api.c)**  
   - Оставить парсинг `projectName`, `openTimeoutMs`, `net` как есть.  
   - Добавить разбор:
     - `doors` → заполнение `cfg.doors[]`, `cfg.doorCount`.
     - `edges` → `cfg.edges[]`, `cfg.edgeCount`.
     - `postCloseTimeouts` → `cfg.postCloseTimeoutMs[globalDoorId - 1]`.
   - Перед разбором **обнулить** соответствующие части `cfg` (`doorCount`/`edgeCount`, используемые элементы массивов), чтобы «полная» конфигурация **заменяла** старую, а не мержила с мусором. (Запись во Flash уже идёт в отдельный слот; «замена» здесь — про содержимое структуры `cfg` в RAM перед persist.)
   - По-прежнему вызывать `Config_Validate` и `Config_Finalize`, затем `ConfigService_Persist`. При ошибке валидации — 400 с `error` в теле.

2. **Парсинг массивов**  
   - Сейчас `json_simple` умеет ключ→значение, объекты, примитивы; **массивы не обрабатываются**.  
   - **Рекомендация: расширить `json_simple`** (а не ручной разбор в `http_api.c`).
     - **Почему не ручной:** при обходе `"doors":[ {...}, {...} ]` нужно корректно пропускать запятые **внутри** строк и объектов. В `comment` могут быть запятые (`"Door 1, main"`) и кавычки; в объектах — вложенные `{...}`. Наивный разбор по `,` или по `{`/`}` без учёта строк ломается на таких случаях. Вся эта логика (quote-/brace-aware) — одна и та же для любых массивов; её лучше реализовать **один раз** в парсере.
     - **Что добавить:** `Json_FindArraySpan(json, key, &out)` — по аналогии с `Json_FindObjectSpan`; итератор по элементам массива (например, `Json_ArrayNextElement` или `Json_ArrayNextObject`), который при обходе учитывает строки и вложенные `{}`/`[]`. Для разбора полей внутри элемента объекта — либо уже существующие `Json_Get*` по span (если передавать в них только фрагмент объекта), либо отдельные `Json_Get*InSpan(span, key, ...)`.
   - Ручной разбор в `http_api` быстрее внедрить «на коленке», но он хрупкий (вложенные запятые/кавычки в `comment`), жёстко завязан на формат и не переиспользуется. Расширение `json_simple` — предпочтительный вариант.

3. **Размер тела запроса и лимиты**  
   - Сейчас `HTTP_BODY_MAX` 2048 байт.  
   - **В первой версии явно ограничиваем:** не более **8 дверей**, разумный лимит по `edges` (например, 16) и по `postCloseTimeouts` (8). Проверять эти лимиты **до** разбора и при превышении возвращать 400.  
   - Оценка: 8 дверей × ~120 байт + несколько edges + 8 postClose + служебные поля ≈ 1.2–1.5 КБ — в 2048 влезает. Поднимать `HTTP_BODY_MAX` пока не требуется.

### UI

4. **«Применить на контроллер»**  
   - Вместо `putConfig(serverConfig)` с урезанным объектом перейти на **`putConfigFull(fullConfig)`**.  
   - В `fullConfig` передавать всё, что уже есть в состоянии редактора: `projectName`, `openTimeoutMs`, `doors`, `edges`, `postCloseTimeouts`, при необходимости `net`. Формат полей — как в `getConfigFull` / в контракте выше.  
   - Запрос отправлять на **`PUT /api/config/full`** (в `api.js` уже есть `putConfigFull` → `/config/full`).

5. **Ошибки и предупреждения**  
   - Убрать или смягчить жёлтое предупреждение «применяются только базовые поля…», когда решим, что firmware действительно принимает полную конфигурацию.  
   - Обработку 400 с `error` от firmware имеет смысл показывать пользователю (как уже делается для merge).

## Как убедиться, что конфигурация применилась

- **Сразу после PUT**: ответ 200, в теле `ok: 1`, при необходимости `seq`. В UART — логи CFG (persist start/done, SaveNew и т.д.) без ошибок.
- **Без перезагрузки**: `GET /api/config/full` возвращает те же `doors`, `edges`, `postCloseTimeouts`, что были отправлены.
- **После перезагрузки**: снова `GET /api/config/full` — конфиг тот же (чтение из QSPI при старте).
- **Поведение контроллера**: Logic Core использует `g_project_cfg` (двери, зависимости, таймауты). Имеет смысл проверить на стенде, что блокировки и таймауты соответствуют применённой конфигурации.

## Риски и ограничения

- **Парсер**: разбор массивов делаем через расширенный `json_simple` (quote/brace-aware), чтобы не ломаться на запятых и кавычках в `comment`. Ограничение длины `comment` (CFG_COMMENT_LEN) по-прежнему важно; экранирование `\` в строках `json_simple` пока не обрабатывает.
- **Размер payload**: при росте числа дверей/edges — либо лимиты, либо увеличение `HTTP_BODY_MAX` и буферов.
- **Валидация**: дубликаты `techId`, неверные `globalDoorId` и т.п. должны отсекаться до persist. Имеет смысл возвращать в 400 понятное `error` (как сейчас для merge).
