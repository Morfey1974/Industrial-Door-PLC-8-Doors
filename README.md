# Industrial Door PLC

**Название проекта:** Industrial Door PLC — прошивка и Web‑интерфейс промышленного контроллера дверей.

**Цели проекта:** Управление электронными замками дверей в чистых помещениях (NO/NC-логика), зависимостями между дверями, конфигурирование и мониторинг через Web без программирования. Реализация по тезисному плану (этапы 0–14).

**Структура проекта:**
- **`Core/`** — STM32 HAL, FreeRTOS, bring-up (LwIP, CAN, RS-485, QSPI).
- **`BSP/`** — GPIO (двери, замки, LED, кнопки).
- **`App/doors/`** — модель двери, DoorTask, DoorHAL.
- **`App/logic/`** — Logic Core, зависимости дверей.
- **`App/system/`** — задачи RTOS (net, CAN, RS-485, HTTP, logger, watchdog, supervisor, comms), EventBus, лог‑очередь.
- **`App/config/`** — формат конфигурации, QSPI, слоты A/B, пароли (SHA-256), RNG.
- **`App/log/`** — журнал событий в QSPI.
- **`WebUI/`** — React (Vite): вход, Dashboard, мониторинг, конфигурация дверей, редактор маппинга.

Документация: **`Documentation/`** (план — `Последовательный тезисный план разработки ПО.pdf`).

## Статус по этапам (тезисный план)

### Этап 0 — Подготовительный (база проекта)
- **0.1** Репозитории FW/Web — разделение прошивки и WebUI.
- **0.2** Окружение: STM32CubeIDE, Visual Studio (опционально для WebUI).
- **0.3** Фиксация версий библиотек (HAL, LwIP, FreeRTOS и т.п.).
- **0.4** Базовая сборка проекта без логики — плата запускается.

### Этап 1 — Аппаратный слой и низкоуровневые драйверы (FW)
- **1.1** Инициализация STM32H723.
- **1.2** Драйверы GPIO (двери, замки, LED, кнопки).
- **1.3** Драйверы таймеров.
- **1.4** Драйвер CAN.
- **1.5** Драйвер RS-485 (UART + направление).
- **1.6** Драйвер Ethernet (RMII + LwIP).
- **1.7** Драйвер QSPI Flash.

Результат: плата запускается, интерфейсы работают независимо.

### Этап 2 — Базовая RTOS-архитектура прошивки
- **2.1** Выбор и настройка FreeRTOS.
- **2.2** Задачи: Door, Logic Core, CAN, RS-485, Ethernet/HTTP, Logger, Watchdog/Supervisor.
- **2.3** Межзадачное взаимодействие (очереди, события, мьютексы).
- **2.4** Базовый watchdog и контроль зависаний.

Результат: прошивка работает как система задач.

### Этап 3 — Аппаратная модель двери (FW)
- **3.1** Объект «дверь».
- **3.2** Работа с датчиком двери.
- **3.3** Управление замком-соленоидом.
- **3.4** Инварианты: запрет блокировки при открытой двери, safe-state при ошибках.
- **3.5** Индикация и зуммер (базовая).
- **3.6** Кнопка Alarm (локальный приоритет).

Результат: одна дверь работает автономно и безопасно.

### Этап 4 — Логика двери и события (FW)
- **4.1** Состояния двери.
- **4.2** События: OPEN/CLOSE, ALARM, тайм-аут.
- **4.3** Тайм-аут открытой двери.
- **4.4** Тайм-аут после закрытия двери.
- **4.5** Сигнализация.

Результат: дверь корректно реагирует на все события. Подробнее: **`Documentation/Спецификация.md`** (NC: окно разблокировки, задержка после закрытия).

### Этап 5 — Logic Core: логика зависимостей дверей (FW)
- **5.1** Модель зависимостей: дверь → список блокируемых дверей.
- **5.2** Обработка события «дверь открылась».
- **5.3** Вычисление списка блокируемых дверей.
- **5.4** Передача команд на двери (локальные и удалённые).
- **5.5** Разрешение конфликтов логики.

Результат: полная логика в Standalone.

### Этап 6 — CAN: Master–Slave архитектура (FW)
- **6.1** Адресация плат (Node ID).
- **6.2** Роль Master/Slave.
- **6.3** Формат CAN-сообщений.
- **6.4** Синхронизация состояний дверей.
- **6.5** Передача логических команд.
- **6.6** Heartbeat и диагностика.
- **6.7** Режим Degraded при потере CAN.

Результат: многоплатная система работает корректно.

### Этап 7 — Хранение данных и журналирование (FW)
- **7.1** Формат конфигурации (`config_format.h`).
- **7.2** Хранение конфигурации в QSPI Flash.
- **7.3** Атомарная активация конфигурации (слоты A/B, commit последним).
- **7.4** Журнал событий: открытия/закрытия, ALARM, ошибки (`event_journal`, QSPI).
- **7.5** Управление износом памяти (кольцевой буфер, статистика).

Результат: система воспроизводима и диагностируема.

### Этап 8 — RS-485 / Modbus RTU (FW)
- **8.1** Modbus RTU Slave (при необходимости).
- **8.2–8.4** Read-only регистры, состояния дверей, ограничения безопасности — по плану.

### Этап 9 — Ethernet и HTTP-сервер (FW)
- **9.1** Запуск Ethernet (LwIP, NetTask).
- **9.2** HTTP-сервер на MASTER (`http_server.c`, `http_task.c`).
- **9.3** REST API: состояние, конфигурация (GET/PUT), журнал (stat, dump); аутентификация по Bearer-токену, роли (super_admin, admin, operator), ограничение попыток входа (5 за 15 мин), CORS из конфига.
- **9.4** Web-сеанс: подключение/отключение, редирект после применения конфигурации.
- **9.5** Аутентификация пользователей: логин/пароль, SHA-256, сессионные токены (RNG), сброс пароля по токену.

Результат: контроллер готов к Web-конфигурированию. План безопасности: **`Documentation/SECURITY_REMEDIATION_PLAN.md`**.

### Этап 10 — Web-приложение: база
- **10.1** Архитектура: React, Vite.
- **10.2** Авторизация и роли (super_admin, admin, operator).
- **10.3** Подключение к контроллеру (API, токен в заголовке).
- **10.4** Отображение состояния системы (Dashboard, /api/state, /api/doors).

Результат: Web видит контроллер и его состояние.

### Этап 11 — Web-конфигуратор
- **11.1** Экран структуры проекта (маппинг).
- **11.2** Экран конфигурирования дверей (общие параметры, двери, зависимости, таймауты).
- **11.3** Экран логики зависимостей (edges в конфиге и UI).
- **11.4** Валидация конфигурации перед отправкой.
- **11.5** Загрузка конфигурации (PUT /api/config, /api/config/full), автосброс платы, редирект на вход.

Результат: полная настройка системы без программирования.

### Этап 12 — Web-мониторинг и журнал
- **12.1** Экран мониторинга дверей.
- **12.2** Карта помещений (режим просмотра маппинга).
- **12.3** Просмотр журнала событий (/api/journal/dump).
- **12.4** Фильтрация и поиск (пагинация, лимит записей).

Результат: удобная эксплуатация объекта.

### Этап 13 — Тестирование и валидация
- **13.1–13.5** Модульные тесты логики, интеграционные тесты, стендовые испытания, тесты отказов, нагрузочные тесты — по плану.

### Этап 14 — Производство и сопровождение
- **14.1–14.4** Серийная прошивка, сервисный режим, документация, релизный цикл — по плану.
